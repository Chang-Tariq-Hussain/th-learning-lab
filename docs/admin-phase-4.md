# Admin — Phase 4 (publishing: edits reach learners)

Until now, edits made in the Question Bank lived only in the database. Phase 4 makes them reach learners —
safely, reviewably and reversibly — without making the learner app depend on the database.

## The model: a content overlay
Learners never query the database. They see **the code registries plus a small overlay** — only the
*differences* between what the database says is published and what the code contains:
- **edited** questions (the new version), **removed** ones (archived / unpublished / taken out of a bank), **added** ones.
- An **empty overlay means "serve the code exactly as before"** — that is the state this ships in.
- It is generated by `npm run content:publish`, written to `src/content/overlay.json` (+ `manifest.json`), and
  **committed**, so a publish is reviewable in git and goes live with a normal deploy.
- Because it is only the diff, it adds almost nothing to the learner bundle (shared JS unchanged at 89.5 kB;
  the only page that grew was the MPT mock runner, by ~2 kB for two edited questions).

## Publish
    npm run content:publish -- --dry-run   # what would change; writes nothing
    npm run content:publish                # writes src/content/overlay.json + manifest.json
    npm run content:publish -- --check     # exit 1 if the committed files are out of date
Then review `git diff src/content`, commit, deploy. **To undo, revert the commit and redeploy** — the previous
overlay returns exactly. The admin **Publishing** page shows what is waiting (edited / new / went live / taken
offline) and what the last publish contains. `DATABASE_URL` (direct connection, operator-only) is needed.

## What reaches learners
| Where | What flows through |
|---|---|
| Quiz banks → standalone quiz pages, GLE Practice, Practice Mode | edits, removals, additions (appended; a quiz question must be **in a bank** and **published**) |
| CSS MPT | **edits** to questions already in a stored mock. A new MPT question reaches learners only once a mock includes it (exam composition is a later phase) |
| PST / JEST / JST | edits, removals, additions, per exam (a question shared by several exams is updated in each, keeping each exam's own filing) |

## Safety
- **Publish refuses — and writes nothing — if it could harm learners:** a code question missing from the
  database (it would be silently dropped; run `db:import`), a stored mock that would lose a question, a quiz bank
  left with no published question, or an overlay that doesn't reproduce the database view when applied to the code.
- **The database stops you earlier:** a question used by a live mock, or the last published question of a bank,
  cannot be archived/unpublished/removed. Exam questions must have exactly 4 options and a valid exam/section;
  quiz questions can only join banks of their own subject. Bank membership changes are audited functions.
- **The learner app is defensive:** every overlay item is validated at load; an invalid, stale or unknown item is
  **ignored** and the code version is served — a bad overlay can never break a quiz, exam or bank, and can never
  empty one. Content Health reports anything ignored (`overlay.ignored-item`).
- Round-trip guarantee: importing the code and mapping it back reproduces **all 5,120 questions identically**
  (`db:verify`), so a pristine database always yields an empty overlay.

## Known limits
- Publishing is a **deliberate deploy step**, not instant. (Deliberate: no learner-facing database dependency, every change reviewable and reversible.)
- Only question content flows through the overlay. Subject/simulation metadata, GLE text, learning paths and exam
  composition still come from code (later phases).
- Quiz bank order: additions are appended; there is no reorder UI yet (the overlay supports an explicit order).
- MFA is still not built; nothing here was run against Supabase's own hosted services.

## One-click publishing (the "Publish to learners" button)
Non-developers publish from **Admin → Publishing**. The button asks GitHub to run `.github/workflows/publish-content.yml`,
which runs `npm run content:publish`, commits `src/content/*` to the branch, and your normal Vercel deploy makes it live.
It refuses (job fails, nothing changes for learners) if publishing could break a quiz or mock. Undo: revert the commit.
Who may click: super admin and question manager (`content.publish` in `src/lib/admin/permissions.ts`). Each click is audited
as `content.publish_requested`.

One-time setup:
1. **GitHub → repo → Settings → Secrets and variables → Actions → New repository secret**: `PUBLISH_DATABASE_URL` = Supabase's
   **Session pooler** connection string (Project settings → Database → Connection string). GitHub runners cannot use the IPv6-only direct host.
2. **GitHub → Settings → Developer settings → Fine-grained tokens**: create a token for this ONE repository with
   *Actions: Read and write*. (Needs nothing else.)
3. **Vercel → Project → Settings → Environment Variables**: `GITHUB_PUBLISH_TOKEN` (the token), `GITHUB_PUBLISH_REPO` (`owner/repo`);
   optional `GITHUB_PUBLISH_BRANCH` (default `main`). Redeploy. Never expose these as `NEXT_PUBLIC_*`.
4. The branch must allow the workflow's push (if `main` requires pull requests, allow GitHub Actions to bypass, or publish from a branch Vercel deploys).
Until steps 1–3 are done the page says one-click publishing is not set up and the command-line steps still work.
Tests: `scripts/e2e-accounts/publish-button.py` (fake GitHub; start the app with `GITHUB_PUBLISH_TOKEN=tok-secret-123 GITHUB_PUBLISH_REPO=acme/lab GITHUB_API_URL=http://127.0.0.1:4010`).
